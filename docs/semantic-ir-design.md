# C++ 编译器第三步：语义分析与中间代码生成设计

## 1. 语义分析与中间代码生成的作用

语法分析器只能判断程序结构是否符合文法，但它并不关心程序是否“有意义”。语义分析的任务，就是在语法正确的基础上继续检查程序的实际含义，并补充类型、作用域、引用关系等信息。

中间代码生成则在语义分析之后进行。它把高层语言结构转换为一种更接近机器执行、但又不依赖具体硬件的表示形式，便于后续做优化和目标代码生成。

这两个阶段通常紧密相连：

- 语义分析负责“解释程序该怎么理解”
- 中间代码生成负责“把这种理解变成可执行的中间表示”

对于本项目来说，这一阶段可以先实现一个清晰的前端语义框架，再生成简单的三地址式中间代码。

---

## 2. 语义分析的基本原理

语义分析不是单纯扫描 Token，而是借助语法树和符号表，对程序进行上下文相关的检查。它通常会处理以下问题：

1. **作用域检查**：变量是否在当前作用域内可见
2. **重定义检查**：同一作用域内是否重复声明同名标识符
3. **未定义检查**：变量、函数、类是否被使用前声明
4. **类型检查**：赋值、表达式、返回值是否类型匹配
5. **参数检查**：当前只在函数定义处登记形参；由于语法层尚不支持函数调用，因此还没有实参与形参匹配检查
6. **控制流检查**：如 `return` 是否出现在函数内部

语义分析通常建立在**语法树遍历**的基础上。也就是说，先拿到 Parser 生成的树，再按节点类型逐个处理。

## 3. 本项目的语义模型设计

为了与现有的词法和语法模块衔接，本项目可以采用如下语义分析模型：

- 以语法分析树作为输入
- 建立分层符号表管理作用域
- 为每个表达式节点推导类型
- 在遍历过程中生成中间代码指令

### 3.1 语义分析目标

本阶段建议先实现以下能力：

- 全局与局部作用域管理
- 变量声明与使用检查
- 简单类型推导
- 赋值语句合法性检查
- `if`、`while`、`return` 等控制结构检查
- 函数和参数符号登记
- 表达式与条件表达式的中间代码生成

当前类语义只覆盖类名和成员声明登记，不支持对象实例化、成员访问或方法调用；逻辑运算按普通布尔运算生成 IR，不具备 C++ 的短路求值语义。

### 3.2 类型系统设计

考虑到当前编译器是教学型子集，类型系统可以先保持简化：

```text
INT
FLOAT
CHAR
BOOL
STRING
VOID
UNKNOWN
```

其中：

- `INT`、`FLOAT`、`CHAR`、`BOOL` 用于基本运算和变量声明
- `STRING` 主要用于字符串常量
- `VOID` 用于函数返回类型
- `UNKNOWN` 用于错误恢复或暂时无法推导的情况

## 4. 符号表与作用域设计

语义分析阶段的符号表比词法分析阶段更完整，它需要记录符号的“语义身份”。

### 4.1 符号表职责

符号表至少应记录：

- 名称
- 类型
- 所属作用域
- 是否为函数 / 变量 / 参数 / 类成员
- 形参列表（函数符号）
- 返回类型（函数符号）
- 声明位置

### 4.2 作用域结构

建议采用**栈式作用域链**：

- 进入 `{}`、函数体、控制块时压入新作用域
- 退出代码块时弹出当前作用域
- 查找符号时先查当前作用域，再向外层回溯

可抽象为：

```java
public class Scope {
    private final Scope parent;
    private final Map<String, SymbolInfo> symbols = new LinkedHashMap<>();
}
```

### 4.3 语义符号信息

可以定义如下结构：

```java
public class SymbolInfo {
    private final String name;
    private final TypeKind type;
    private final SymbolKind kind;
    private final int line;
    private final int column;
}
```

其中 `SymbolKind` 可以包括：

- `VARIABLE`
- `PARAMETER`
- `FUNCTION`
- `CLASS`
- `FIELD`

### 4.4 作用域查找策略

查找一个标识符时：

1. 先看当前作用域
2. 如果没有，向父作用域递归查找
3. 若都找不到，报告未定义错误

这种策略与大多数块作用域语言一致，也适合当前项目结构。

## 5. 语义检查规则设计

### 5.1 变量声明检查

变量声明时，需要检查：

- 同一作用域内是否已有同名变量
- 声明类型是否有效
- 是否带初始化表达式

例如：

```cpp
int a = 10;
```

应先登记 `a`，再分析初始化表达式是否能赋给 `int`。

### 5.2 赋值语句检查

赋值语句需要检查：

- 左侧标识符是否已声明
- 右侧表达式类型是否可赋给左侧类型

例如：

```cpp
int a;
a = 3.14;
```

如果不允许隐式截断，就应报告类型不匹配。

### 5.3 表达式类型推导

表达式类型推导可以采用规则驱动方式：

- `INT + INT -> INT`
- `INT + FLOAT -> FLOAT`
- `CHAR` 在需要时可提升为 `INT`
- 关系运算和逻辑运算结果为 `BOOL`

可以先实现基础版本，不展开复杂的隐式转换体系。

### 5.4 条件与循环检查

对于 `if`、`while` 的条件表达式：

- 条件应能推导为 `BOOL` 或可转换为布尔值的表达式
- 若条件明显不可用，应提示类型错误

### 5.5 返回语句检查

返回语句应满足：

- 非 `void` 函数中不能缺少返回值
- 返回值类型需与函数声明返回类型兼容
- `void` 函数中不应返回表达式

## 6. 语义分析的遍历策略

语义分析最常见的实现方式，是对语法树进行递归遍历。

### 6.1 自顶向下递归遍历

每个语法树节点对应一个处理函数：

- `visitProgram`
- `visitDecl`
- `visitStmt`
- `visitExpr`
- `visitPrimary`

这种方式直观清晰，和语法结构一致。

### 6.2 基本流程

1. 从根节点开始遍历
2. 遇到声明节点时登记符号
3. 遇到表达式节点时推导类型并生成临时值
4. 遇到语句节点时生成相应中间代码
5. 若发现语义错误，立即记录或抛出异常

---

## 7. 中间代码的形式选择

中间代码有很多种形式，例如：

- 三地址码
- 四元式
- 逆波兰式
- SSA 中间表示

本项目适合采用**三地址码**或其等价的四元式表示，因为它简单、直观，便于教学和后续扩展。

### 7.1 三地址码特点

三地址码通常形如：

```text
t1 = a + b
t2 = t1 * c
if t2 < 10 goto L1
goto L2
```

其优点是：

- 接近机器指令
- 便于优化
- 结构清晰

### 7.2 四元式表示

四元式可表示为：

```text
(op, arg1, arg2, result)
```

例如：

```text
(+, a, b, t1)
(*, t1, c, t2)
(<, t2, 10, t3)
(jz, t3, -, L2)
```

这种形式更适合存储和后续优化。

## 8. 中间代码生成设计

中间代码生成可在语义分析遍历过程中同步完成。换句话说，边检查边生成。

### 8.1 生成原则

- 表达式先生成子表达式，再生成当前节点结果
- 每次计算都使用新的临时变量
- 控制流通过标签和跳转指令表达
- 赋值通过一个简单的复制指令完成

### 8.2 临时变量与标签

建议维护两个计数器：

- 临时变量计数器：`t1`、`t2`、`t3`...
- 标签计数器：`L1`、`L2`、`L3`...

例如：

```java
String newTemp() {
    return "t" + tempIndex++;
}

String newLabel() {
    return "L" + labelIndex++;
}
```

### 8.3 中间代码指令设计

可先定义一个统一的指令结构：

```java
public record Quadruple(String op, String arg1, String arg2, String result) {}
```

常见操作包括：

- 算术运算：`+`、`-`、`*`、`/`、`%`
- 关系运算：`<`、`<=`、`>`、`>=`、`==`、`!=`
- 赋值：`=`
- 跳转：`j`, `jz`, `jnz`
- 标签：`label`
- 返回：`return`

### 8.4 表达式生成示例

对于：

```cpp
a + b * c
```

中间代码可生成：

```text
t1 = b * c
t2 = a + t1
```

即先处理高优先级乘法，再处理加法。

### 8.5 条件语句生成示例

对于：

```cpp
if (a < b) {
    x = 1;
} else {
    x = 2;
}
```

可生成：

```text
t1 = a < b
jz t1, L1
t2 = 1
x = t2
goto L2
L1:
t3 = 2
x = t3
L2:
```

## 10. 错误处理设计

语义阶段的错误通常比语法错误更具体，也更需要上下文信息。

常见错误包括：

- 变量未声明
- 重复定义
- 类型不兼容
- 函数参数不匹配
- 返回值类型不一致

建议错误信息包含：

- 错误类型
- 具体位置
- 相关标识符名称
- 当前与期望类型

例如：

```text
语义错误：变量 a 未声明，位置：第 5 行，第 9 列
```

---

## 11. 与语法分析器的衔接方式

语义分析建立在语法树之上，因此其输入应是 Parser 生成的 `ParseTreeNode`。

处理流程建议为：

1. Lexer 生成 Token 列表
2. Parser 生成语法树
3. SemanticAnalyzer 遍历语法树并建立符号表
4. IRGenerator 生成中间代码
5. 输出语义检查结果与中间代码

这种分层结构清晰，也便于日后替换某一阶段实现。
